# Vault Cloud — self-serve console + branded domains · try it

**2026-07-02.** The Vault Cloud is **live on real domains** in the *Unforced
Development* Cloudflare account (id `8f2a7eb9d5e21ffa902a76cf62975c82`, which
holds the `parachute.computer` zone). There is now a **self-serve console** at
[`cloud.parachute.computer`](https://cloud.parachute.computer) — create an
account, create vaults, connect your AI — plus **per-vault ownership** enforced
at the issuer (a user can only mint a token for a vault they own). No payment;
free while in beta. The whole path (signup → vault → connect AI → write → export,
and the ownership refusal) is validated end-to-end by `scripts/smoke-dev.ts`
(**29/29 green**).

## The console (`cloud.parachute.computer`)

The self-serve front door, server-rendered on the identity worker:

1. **`/signup`** / **`/login`** — **magic-link by default**: enter an email,
   `POST /auth/magic` emails a single-use link (10-min TTL, stored hashed),
   `GET /auth/verify?token=…` consumes it and signs you in. The first link for a
   new address doubles as signup (a passwordless account, `email_verified` from
   the start). "Use a password instead" is a `<details>` disclosure — password
   stays a supported secondary path. The neutral "check your email" response is
   identical whether or not the address has an account (no enumeration).
2. **`/logout`** — clears the cloud session (the same cookie the OAuth consent
   flow uses, so signing in carries through connect-your-AI). Both password login
   paths (console + OAuth authorize) have a per-(IP,email) brute-force lockout
   after 5 failures; magic-link sends have a per-(IP,email) fence too.
3. **`/console/security`** — enroll **optional TOTP 2FA** (QR + manual secret,
   confirm a code, one-time backup codes) or set/change the optional password.
   When 2FA is on, both magic-link and password logins divert through
   `/login/2fa` before any session is minted.
4. **`/console`** — your vaults + a create form + a per-vault **connect card**
   (the `claude mcp add …` command, the MCP endpoint, the REST base).
5. **`POST /console/vaults`** — claim a name (slug `^[a-z0-9][a-z0-9-]{1,62}$`,
   reserved-name list). The DO materializes on first use.

**Vault DELETE is deliberately absent in v1** — irreversible-action UX (typed
confirmation, grace window) is a later phase; noted, not built.

**Ownership is enforced at the issuer.** A `vault:<name>:*` token is minted only
for a vault the authenticated user owns — checked at auth-code issuance AND at
the token endpoint (defense-in-depth). An unowned name is refused with
`invalid_scope` naming the vault. This closed the pre-existing hole where the
single dev user could mint for any vault name.

## Connect Claude Code to a vault

The console prints this per vault; for `demo`:

```sh
claude mcp add --transport http parachute-demo \
  https://u.parachute.computer/vault/demo/mcp
```

On first use Claude walks the discovery chain automatically (verified live): the
MCP `401` carries `WWW-Authenticate: resource_metadata=…`, which points at the
vault's protected-resource doc, which names the identity worker as the
authorization server. Claude does DCR, opens the browser to the identity login,
you sign in with the **dev credential**, approve, and Claude gets a resource-
narrowed token (`aud=vault.demo`, scope `vault:demo:read vault:demo:write`).

You can only connect vaults **you own** — create them in the console first.
Reserved names (`www`, `api`, `admin`, `cloud`, `notes`, `demo`, …) can't be
claimed. Each vault is its own isolated DO.

## The dev credential

Lives in **`workers/identity/.dev-secrets`** (gitignored — `DEV_USER_EMAIL` +
`DEV_USER_PASSWORD`; the email is `dev@parachute.computer`). The password is a
random 24-char string generated at seed time; it is **not** in this repo or this
report. The seed generator hashes it (PBKDF2-SHA256) into the identity D1
`users` table via `scripts/seed-dev-user.sql` (also gitignored). To reseed or
rotate: edit `.dev-secrets`, then `bun scripts/seed-dev-user.ts && wrangler d1
execute parachute-identity --remote --file=./scripts/seed-dev-user.sql`.

## Magic-link email — dev-log now, real email needs Aaron

The magic-link send is behind an `EmailSender` interface (`workers/identity/src/email.ts`):

- **Now (dev):** no sending domain is onboarded, so the worker uses the **dev-log
  sender** — it logs the link (`wrangler tail`) and, because `ENVIRONMENT` is
  `"development"`, echoes it in an **`x-parachute-dev-magic-link`** response
  header. That's how `smoke-dev.ts` and manual testing complete the flow without
  an inbox. **This header is a dev-only affordance — a prod deploy MUST set
  `ENVIRONMENT="production"`, which drops it.**
- **To flip to real email (Aaron, ~2 min, one-time):**
  1. **Onboard the sending domain.** Dashboard → **Compute & AI → Email Service →
     Email Sending → Onboard Domain** → `parachute.computer` → **Add records and
     onboard** (or `wrangler email sending enable parachute.computer`). Because
     the `parachute.computer` zone is already in the Unforced Development account,
     Cloudflare adds the **SPF (TXT) + DKIM (CNAME)** records automatically; a
     `DMARC` TXT is a recommended manual add. Propagates in ~5–15 min.
  2. **Uncomment the binding** in `workers/identity/wrangler.toml`:
     ```toml
     [[send_email]]
     name = "EMAIL"
     ```
     and redeploy (`bash scripts/deploy-dev.sh`). The worker auto-detects the
     bound `EMAIL` and uses it — **no code change** (`src/index.ts` `senderFor()`).
  - Cloudflare Email Sending is **public beta** (announced 2026-04-16) and needs
    the **Workers Paid** plan (this account has it). New accounts start with a
    conservative daily send quota that scales with reputation; 50 recipients max
    per message. FROM address is `EMAIL_FROM` (`noreply@parachute.computer`).

The last seven are the new magic-link + TOTP flow: a passwordless account is
created by verifying an emailed (dev-log) link, the link is single-use, TOTP is
enrolled on `/console/security`, and a subsequent magic sign-in then **diverts to
`/login/2fa`** and only mints a session once the code is verified. Before those,
the console + ownership flow: a fresh throwaway user signs
up, creates a vault, mints a token via the real authorize flow, writes a note in
their vault — and the dev user is **refused** (`invalid_scope`) a token for that
same vault. `iss` is now `https://cloud.parachute.computer` and the services
catalog resolves to `https://u.parachute.computer/vault/<name>`.

So: self-serve console (signup/login/vaults) · vault ownership enforcement ·
OAuth issuer (DCR + PKCE-S256 + login/consent + real RS256 JWT + resource-narrowed
scope + refresh) · vault REST CRUD · MCP (initialize + tools/list + tools/call,
correct `Accept` negotiation) · SSE live-query snapshot · portable-md export
tarball. Test suites stay green (vault 86 +1 todo, **identity 71** = 42 original +
29 new console/ownership/throttle) and typecheck clean.

The `services` catalog URL is now `https://u.parachute.computer/vault/<name>` —
the real, reachable branded host (no longer cosmetic). The token's `aud`+`scope`
remain the enforced gates; the catalog just tells clients where the vault lives.

## A real bug this deploy caught (fixed)

Live verification earned its keep: **workerd caps PBKDF2 at 100,000 iterations**
(`deriveBits` throws `NotSupportedError` above it). `users.ts` used 210,000 (the
hub's number). The vitest-pool workerd did **not** enforce the cap, so the 42/42
conformance suite passed — then every real login `500`'d on the deployed worker.
Fixed to 100,000 (workerd's max) in `users.ts` + `seed-dev-user.ts`, hardened
`verifyPassword` to fail-closed on any crypto error instead of 500, re-seeded,
redeployed → login green. (Classic prod-vs-test divergence; only the live deploy
surfaces it.) **Follow-up:** 100k < current OWASP guidance for PBKDF2-SHA256 —
a stronger KDF (chained rounds, or scrypt/argon via WASM) is worth a cloud issue
before this tier is a paid product.

## Domains — what's live, what needs Aaron

**Live now (no action needed):** `cloud.parachute.computer` (console + issuer)
and `u.parachute.computer` (vaults, path routing) are attached as Workers Custom
Domains in the Unforced Development account, which holds the `parachute.computer`
zone (id `0801a8b9…`). The stored wrangler OAuth token could **create Workers
Custom Domains** (via `workers_scripts`/`ssl_certs` scope) even though it lacks
direct DNS-edit — CF provisions the DNS + cert internally for a custom domain.

**The one thing NOT achievable with this token — per-vault subdomains
(`<name>.u.parachute.computer`):** a wildcard needs a **proxied wildcard DNS
record** (`*.u.parachute.computer`) which is (a) Enterprise-gated on this Free
zone and (b) needs `#dns_records:edit`, which the OAuth token does **not** carry
(a reversible TXT-record write test returned `Authentication error` / code 10000;
`wrangler whoami` shows `zone (read)` only). Path routing on the single branded
host is the shipped shape — the vault router already serves the subdomain form
too, so when the wildcard lands nothing in the app changes. **To enable
subdomains later, Aaron needs to:** (1) upgrade the zone to a plan that allows
proxied wildcard DNS (or add the record + `*.u.parachute.computer/*` Workers
route by hand in the dashboard), and (2) grant a token with `#dns_records:edit`
if doing it via API/wrangler. Then unset `VAULT_ORIGIN` on the identity deploy
(flips cards + catalog to the subdomain form).

**Still gated on Aaron (unchanged):**
- **Stripe / control plane.** No billing or provisioning worker yet (design §6
  Phase 5). This is the no-payment beta.
- **Stronger KDF.** PBKDF2 at 100k (workerd's cap) is below current OWASP
  guidance — worth a cloud issue before this tier is a paid product (see below).
- **`[env.production]` split.** Today one environment fronts both the dev and the
  "real" domain (same D1/R2/DO). A separate prod environment with its own
  bucket/D1 is a later phase.

## Known limitations (by design, this phase)

- **Async-batch atomicity.** A multi-note POST goes through core's
  `transactionAsync`, which the sync-only DO `transactionSync` can't wrap, so it
  still emits an intercepted `BEGIN IMMEDIATE`/`COMMIT` (2 no-ops per batch)
  rather than a real DO transaction — a mid-batch throw won't roll back. Tracked
  by the cloud#26 tripwire (see `workers/vault/src/shim.ts`). Single-note writes
  and every free-`transaction()` op (renameTag/mergeTags/createNotes + boot
  migrations) **are** DO-atomic.
- **Attachment binaries not in export.** The export sink is synchronous, so it
  can't `await` R2 to copy attachment bytes — frontmatter refs are emitted
  (structurally complete + importable), binaries are not. Matches a bun
  markdown-only export.
- **No scribe.** Cloud v1 is data-only; the attachment POST records the row but
  enqueues no transcription (there's no scribe worker in cloud).
- **workers.dev path routing.** Subdomain addressing (`<name>.u.parachute.computer`)
  and its wildcard cert are a domain-day thing; tonight is `/vault/<name>/*`.
- **Export tarballs accumulate.** Every `/api/export` writes a new tarball under
  `vault-<name>/exports/` in R2 and nothing prunes them yet — an R2 lifecycle
  rule / GC alarm is a pre-real-launch ops TODO (noted in `vault-do.ts`).
