## Connect Claude Code to a dev vault

```sh
claude mcp add --transport http parachute-demo \
  https://parachute-vault-do.unforced.workers.dev/vault/demo/mcp
```

On first use Claude walks the discovery chain automatically (verified live): the
MCP `401` carries `WWW-Authenticate: resource_metadata=…`, which points at the
vault's protected-resource doc, which names the identity worker as the
authorization server. Claude does DCR, opens the browser to the identity login,
you sign in with the **dev credential**, approve, and Claude gets a resource-
narrowed token (`aud=vault.demo`, scope `vault:demo:read vault:demo:write`).

Any vault name works — swap `demo` for `notes`, `scratch`, etc. (each is its own
isolated DO). Reserved names (`id`, `www`, `api`, `app`, `admin`, `notes`,
`cloud`) are only reserved for the *subdomain* form, which isn't live tonight;
path routing accepts them, but keep off them to stay forward-compatible.

## The dev credential

Lives in **`workers/identity/.dev-secrets`** (gitignored — `DEV_USER_EMAIL` +
`DEV_USER_PASSWORD`; the email is `dev@parachute.computer`). The password is a
random 24-char string generated at seed time; it is **not** in this repo or this
report. The seed generator hashes it (PBKDF2-SHA256) into the identity D1
`users` table via `scripts/seed-dev-user.sql` (also gitignored). To reseed or
rotate: edit `.dev-secrets`, then `bun scripts/seed-dev-user.ts && wrangler d1
execute parachute-identity --remote --file=./scripts/seed-dev-user.sql`.

## A real bug this deploy caught (fixed)

Live verification earned its keep: **workerd caps PBKDF2 at 100,000 iterations**
(`deriveBits` throws `NotSupportedError` above it). `users.ts` used 210,000 (the
hub's number). The vitest-pool workerd did **not** enforce the cap, so the 42/42
conformance suite passed — then every real login `500`'d on the deployed worker.
Fixed to 100,000 (workerd's max) in `users.ts` + `seed-dev-user.ts`, hardened
`verifyPassword` to fail-closed on any crypto error instead of 500, re-seeded,
redeployed → login green. (Classic prod-vs-test divergence; only the live deploy
surfaces it.) **Follow-up:** 100k < current OWASP guidance for PBKDF2-SHA256 —
a stronger KDF (chained rounds, or scrypt/argon via WASM) is worth a cloud issue
before this tier is a paid product.

## Known limitations (by design, this phase)

- **Async-batch atomicity.** A multi-note POST goes through core's
  `transactionAsync`, which the sync-only DO `transactionSync` can't wrap, so it
  still emits an intercepted `BEGIN IMMEDIATE`/`COMMIT` (2 no-ops per batch)
  rather than a real DO transaction — a mid-batch throw won't roll back. Tracked
  by the cloud#26 tripwire (see `workers/vault/src/shim.ts`). Single-note writes
  and every free-`transaction()` op (renameTag/mergeTags/createNotes + boot
  migrations) **are** DO-atomic.
- **Attachment binaries not in export.** The export sink is synchronous, so it
  can't `await` R2 to copy attachment bytes — frontmatter refs are emitted
  (structurally complete + importable), binaries are not. Matches a bun
  markdown-only export.
- **No scribe.** Cloud v1 is data-only; the attachment POST records the row but
  enqueues no transcription (there's no scribe worker in cloud).
- **workers.dev path routing.** Subdomain addressing (`<name>.u.parachute.computer`)
  and its wildcard cert are a domain-day thing; tonight is `/vault/<name>/*`.
- **Export tarballs accumulate.** Every `/api/export` writes a new tarball under
  `vault-<name>/exports/` in R2 and nothing prunes them yet — an R2 lifecycle
  rule / GC alarm is a pre-real-launch ops TODO (noted in `vault-do.ts`).
