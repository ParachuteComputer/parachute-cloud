# Parachute Cloud

`@openparachute/cloud` — the **Vault Cloud**: Parachute's hosted offering ("pay us money, get a vault") on Cloudflare, plus the (to-be-revived) billing/provisioning control plane. **Reborn 2026-07-02** as a Workers monorepo per the decided direction — see `parachute.computer/design/2026-07-02-vault-cloud-serverless-design.md` (the design of record) and `Decisions/2026-07-02-cloud-do-per-vault` in the team vault.

> **The old Fly-Machines-per-user architecture this file used to describe is DEAD** (runtime discarded 2026-07-02; its billing/lifecycle *design* in `src/` is harvest material for the control-plane revival). If you're reading git history: everything pre-2026-07 describes the discarded shape.

## Mental model

> **One Durable Object per vault.** The DO's SQLite *is* the vault (schema (current SCHEMA_VERSION from `@openparachute/core`) via `@openparachute/core` behind a `Database`-shaped shim); its isolation is the tenant boundary — a vault's code cannot address another tenant's data. Scale-to-zero: hibernated vaults bill ~storage only. Shared core + shared wire contract with the self-hosted bun vault; the runtime around core deliberately diverges (bounded, per the design's shared-vs-forked ledger).

## Load-bearing gotchas

- **Stale `file:` dep**: `workers/vault` depends on `@openparachute/core` via `file:../../../parachute-vault/core`. Bun COPIES it into node_modules at install — after any vault-core change, `bun install` (or rm the `.bun` core dir) or you test/deploy against stale core. Both deploy scripts do this automatically; test runs don't.
- **Transactions**: DO SQLite rejects `BEGIN/COMMIT`. Core's `transaction()` duck-types the shim's `transactionSync` (→ `ctx.storage.transactionSync`) since vault 0.6.5-rc.2. The conformance suite pins a GLOBAL-zero interception count; the sole residual is the async-batch path (cloud#25 — close or accept before real clients batch-write).
- **workerd ≠ vitest-workerd exactly**: workerd caps PBKDF2 at 100k iterations at runtime but vitest's pool does NOT enforce it (42/42 green while every live login 500'd). Live-smoke after deploy, always (`scripts/smoke-staging.ts` / `scripts/smoke-prod.ts`).
- **TEST_JWKS** in workers/vault auth is double-gated on `ENVIRONMENT="test"` — never set that in a deployed config.
- **Observability (since 0.0.8-rc.8)**: `[observability] enabled = true` (+ `head_sampling_rate = 1`) in BOTH wrangler.tomls, top-level AND `[env.staging.observability]` (NOT inherited by named envs) — before this the account had no persistent Workers Logs at all (`wrangler tail` captured zero events, 2026-07-02). The identity worker carries the ops cron (`[triggers]`, patterns must match `HEALTH_CRON`/`DIGEST_CRON`/`DRIP_CRON`/`USAGE_CRON` in `src/ops.ts`): every 10 min a health check (D1 self-check + `GET <VAULT_ORIGIN>/health`; failures email `OPERATOR_ALERT_EMAIL` with a 1-hour per-check dedupe in D1 `ops_alerts`), Mondays 14:00 UTC a counts-only ops digest (users/vaults/magic-link events — the `magic_link_events` per-day counters are PII-free by design), hourly at :15 the onboarding drip (`src/drip.ts` — see the drip note below), and daily 03:30 UTC the usage rollup (`src/usage.ts` — see the usage note below). Staging runs the same crons but its devlog sender writes the emails to the worker log instead. Live cron firings can't be forced — `wrangler dev --test-scheduled` + `curl "http://localhost:8787/__scheduled?cron=..."` locally, `worker.scheduled` via `createScheduledController` in vitest; for the drip and the usage rollup specifically, staging additionally exposes `POST /__test/drip-run` and `POST /__test/usage-run` (both 404 in production) so the live smoke can drive a tick deterministically.
- **Onboarding drip (since 0.0.8-rc.12, ratified)**: three behavior-aware emails, never marketing-brained — day-0 welcome (within the hour of signup: the vault's three doors), day-3 connect-your-AI nudge ONLY when the account shows no AI activity (no `tokens` or `grants` row for a non-`parachute-console` client), day-14 feedback ask (Reply-To `hello@parachute.computer`). Exactly-once via the `drip_sends` ledger (send-then-record; a failed send retries next hour); eligibility windows are wider than the cron interval on purpose (missed-run tolerance — the ledger, not the window edge, prevents resends); `DRIP_RUN_CAP` (50 attempts/run) drains backlogs gradually. Every email carries a tokenized unsubscribe link (`users.drip_unsub_token`, raw-stored 256-bit random — it only authorizes opting out) + RFC 8058 `List-Unsubscribe`/`List-Unsubscribe-Post` headers; `GET|POST /unsubscribe?t=…` is loginless and idempotent, honored by every eligibility query (`users.drip_unsubscribed`). Counters in `drip_events` (PII-free, the `magic_link_events` pattern). Migration 0008.
- **Plans — the entitlement layer (since 0.0.8-rc.13; the pricing-model rewrite landed 2026-07-05)**: `users.plan` (migration 0009; new signups start on `'trial'`, `createUser`) + `workers/identity/src/plans.ts` as the SINGLE SOURCE of plan truth. **The tier ladder** (notes caps dialed down 2026-07-06 — notes are TEXT, the R2 attachment meter is separate; start-small-grow-later + higher margins): Entry (1 vault · 100 MB notes · NO attachments · NO voice · $1), Standard (3 vaults · 250 MB notes · 2 GiB attach · 60 voice-min · $3/mo), Plus (5 vaults · 500 MB notes · 8 GiB attach · 300 min · $5/mo), Power (10 vaults · 1 GiB notes · 50 GiB attach · 1200 min · $10/mo). Two state-machine plans complete it: `trial` (30-day no-card; entitlements mirror the CHOSEN tier when `pending_plan` names a purchasable one — `entitlementPlanFor`, rc.31, "try any plan free for 30 days" — else Plus flat; the day-30 sweep FLOORS a paid-tier pending on a trial to `expired`, never a free upgrade) auto-downgrades to `expired` (the post-trial FLOOR: 0 new vaults, notes/attach writes FROZEN → **402 `plan_required`**, reads + export + DELETE untouched — "your notes are safe"). Storage is now a **TWO-METER cap** — the SQLite graph vs `notes_bytes` and R2 attachments vs `attachment_bytes` as SEPARATE budgets pushed as `caps: {notes_bytes, attachment_bytes}` (`attachment_bytes: 0` = the Entry notes-only tier → uploads 403 `attachments_not_included`); the `frozen` flag is the expired floor the DO checks BEFORE any cap math. The paywall + cap gate bites on BOTH the REST write path AND the `/mcp` write verbs (verb-aware, per-tool — read + delete verbs pass, mirroring REST's DELETE exemption). Vault-count is enforced at `POST /console/vaults` (friendly at-cap message; users already OVER a cap are grandfathered — they keep/mint everything they own, only NEW creation is refused). The storage cap is PUSHED into each vault DO at creation (and via `applyPlanToVaults`, the seam admin/Stripe will call on plan change) through the #51 mint seam with verb `admin`: `PUT /vault/<name>/api/internal/config {cap_bytes}`. **The vault-side gate is the first-party `client_id`** (`parachute-console`, vault-call.ts ↔ workers/vault/src/auth.ts `FIRST_PARTY_CLIENT_ID`) — scope/verb alone can't distinguish platform from tenant because a vault owner can mint `vault:<name>:admin` via public OAuth; DCR ids are server-generated UUIDs so the claim is unforgeable. The internal endpoint dispatches BEFORE the DO cap gate (a plan upgrade must be able to raise the cap of a full vault); the create-time push is best-effort (a miss leaves the more-generous 1 GiB env default; reconcile via `scripts/backfill-plans.ts`, the one-time comp+cap backfill that mints operator-side tokens from the D1 signing key). **V1 cap semantics**: per-vault cap = plan `total_bytes` ("every vault ≤ total"), NOT a cross-vault aggregate — the daily usage rollup (below) RECORDS the truth; the ENFORCEMENT tightening to a real shared budget ships with the billing PR, deliberately not before. The resolved cap surfaces read-scoped on the vault landing (`cap_bytes`, a cloud-only additive field).

- **GFS snapshots + paid restore (since 0.0.8-rc.18, Wave 4e)** — nightly 04:00 UTC (`SNAPSHOT_CRON`, after the 03:30 usage rollup) the identity worker asks each vault DO to snapshot itself (`POST /api/internal/snapshot`, the first-party mint seam) under the OWNER'S PLAN retention (plans.ts): **paid 14 daily / 8 weekly / 12 monthly; free 0/1/0 — ONE rolling weekly, an internal disaster-recovery artifact (ours; never surfaced, the console shows free users only the History teaser)**. The rotation lives vault-side (`workers/vault/src/snapshots.ts`): **rank-at-birth GFS** — every snapshot is `daily`; the first snapshot of an ISO week is ALSO `weekly`; the first of a UTC month ALSO `monthly`; retention keeps the newest N per rank (survive-under-any-rank); a snapshot that nothing would retain is **skipped before the export work** (that's why free vaults export weekly, not nightly). Tarballs = the SAME core export engine as `/api/export`, written to `vault-<name>/snapshots/<server-ts>.tar` + a `manifest.json` **in R2, next to the tarballs** (chosen over DO storage because (1) restore runs in a DIFFERENT DO which can only reach R2, and (2) the manifest must survive losing the DO — the exact disaster snapshots guard against); single-writer holds (only the vault's own DO writes its manifest); a corrupt manifest FAILS the run (an empty read would mass-prune). **Quota honesty: `snapshots/` never touches the r2_bytes cap meter** (no meterAdd/meterSub — the exports/ posture, conformance-pinned), and internal dispatch precedes the cap gate so a FULL vault still snapshots. The import engine is core's `importVault` behind a `TarImportSource` (`workers/vault/src/restore.ts`) — the same seam as the bun CLI's import, so notes/tags/links/schemas/timestamps round-trip byte-equal (conformance-pinned via export comparison). **v1 attachments caveat (say it everywhere user-facing)**: SNAPSHOTS carry NO attachment binaries (the snapshot path runs the export engine without the attachment index; the on-demand `/api/export` DOES stream binaries since 0.0.8-rc.25) — a restore recreates attachment ROWS/references, the FILES are absent; the History section + the success notice both carry this. - **Voice transcription + the $5 Voice tier (since 0.0.8-rc.19, cloud#56)** — the eternal-"Transcribing…"-spinner fix. A `transcribe:true` attachment link (`POST /vault/<name>/api/notes/:id/attachments`) used to no-op; now it stamps the attachment `transcribe_status: pending` + `transcribe_origin: "legacy"`, marks the note `transcribe_stub: true`, and arms a **DO alarm** (`VaultDO.alarm()` — the DO's first + only alarm user). The alarm drains pending attachments FIFO, **ONE inference per wake** (whisper-turbo runs up to ~240 s as an I/O subrequest; re-arms if more remain), reads the R2 audio, and calls a `WorkersAiProvider` (`workers/vault/src/transcription/workers-ai.ts`, implementing core's `TranscriptionProvider` seam from vault#529) → `@cf/openai/whisper-large-v3-turbo`. **Spike constraints baked in** (2026-07-03): audio is a **base64 STRING** via a **ZERO-COPY `Buffer` view** (`Buffer.from(audio.buffer, byteOffset, byteLength)`, NOT `Buffer.from(uint8array)` which copies), **25 MB raw ceiling** (`MAX_TRANSCRIBE_BYTES` — the encode peaks ~2.33× raw, and an OOM in the synchronous encode is UNCATCHABLE, so the ceiling is **head-size-gated BEFORE the R2 read + encode** in `transcribeOne`; over → non-retriable `audio_too_large`; see the constant's memory math for why 25 not 45), and a **`4002`/too-long inference error is TERMINAL** (`audio_too_long` — never blind-retry, each burns ~4 min). Metering rides `transcription_info.duration` (the `usage` field is all-zeros). On success the alarm surgically replaces `_Transcript pending._` with the transcript (mirroring the self-host body policy — `src/transcription/pipeline.ts`: replace-or-append, `if_updated_at`-guarded), meters `audioSeconds/60`, and honors `audio_retention` (until_transcribed/never drop the R2 audio + decrement the storage meter). Failure → 3-attempt backoff then `_Transcription unavailable._`. **Plan gating**: voice is no longer a standalone tier (the 2026-07-05 pricing rewrite) — `plans.ts` bundles it into Standard/Plus/Power (60/300/1200 monthly minutes; Entry has none); the entitlement `{enabled, minutes_limit}` is pushed into each vault DO's config alongside the two-meter `caps` (vault-call.ts `pushVaultCap`/`applyPlanToVaults`), and the **landing** (`GET /vault/<name>`) surfaces `transcription: {enabled, minutes_remaining}` (Notes gates the mic on it — free = `enabled:false`, honest). The monthly **soft cap** is a per-DO `transcribe_minutes` meter (the r2_bytes meter pattern, UTC-month-tagged, lazy reset): over budget → a distinct `_Monthly voice limit reached…_` marker, text never blocked. ## Security posture (identity worker, settled 2026-07-02)

- **CORS split (#35, intentional divergence from the hub)**: wildcard-uncredentialed on `/oauth/token` + `/oauth/revoke`, reflected-Origin+credentials on `/oauth/register`, **no CORS headers at all on `/oauth/authorize`** (pinned by a negative conformance test). The hub applies echo-Origin+credentials uniformly across `/oauth/*`; the cloud split is strictly more conservative, and every wire BODY stays hub-identical. Both CORS helpers expose `WWW-Authenticate` (hub parity). Canonical doc: the posture block in `workers/identity/src/oauth-shared.ts`.
- **KDF (#28, the honest version)**: workerd caps PBKDF2 at 100k iterations and ships no argon2 — 100k is the runtime's ceiling and we don't pretend otherwise. Verifiers are PBKDF2-**SHA512**@100k (versioned format; legacy sha256 hashes verify and transparently re-hash on next successful password login). The actual defenses are architectural: passwords are an **optional secondary** factor (magic-link primary), the DO rate limiter (#30) blunts online guessing, TOTP 2FA is available, and the D1 password store never crosses the wire. Full note: `workers/identity/src/users.ts`.
- **CSP (P0.2, 0.0.8-rc.53)**: EVERY server-rendered page carries a `Content-Security-Policy`, attached at the single HTML choke point `htmlResponse` (`oauth-shared.ts`) — so JSON/machine endpoints (token/JWKS/webhook) never get one. Strict ceremony policy: `default-src 'none'`; `script-src 'self' 'nonce-<per-response>'` (NO `'unsafe-inline'` for script — the one inline script, the console's create-moment/clipboard/checklist JS, is admitted only by a **per-response 128-bit nonce**); `style-src 'self' 'unsafe-inline'` (the pages carry inline `<style>` blocks AND 100+ inline `style="…"` attributes — a nonce covers `<style>` ELEMENTS but not style attributes, so `'unsafe-inline'` for styles is the pragmatic, low-risk choice; refactoring the attribute styles out is a later cleanup); `connect-src 'self'` (the console script's same-origin fetches); `form-action 'self'` (every form posts same-origin — billing's checkout form posts same-origin then the worker 302s to Stripe, which form-action does NOT govern); `img-src 'self' data:`, `frame-ancestors 'none'`, `base-uri 'none'`, `object-src 'none'`. **The nonce mechanism**: a template stamps the marker `NONCE_ATTR` (= `nonce="__CSP_NONCE__"`) on inline `<script>`; `htmlResponse` mints one nonce per response, substitutes it into the body, and emits the matching `'nonce-…'` in the header — header and body agree by construction. Injection-safe: `esc()` turns every `"` into `&quot;`, so the marker (which needs literal double-quotes) can only come from a trusted template, never user data. **Per-route ready (PW4 two-tier connect-src)**: `contentSecurityPolicy(nonce, opts)` RETURNS the policy string (not a constant), so Phase 1's SPA route (served from Static Assets on the same origin) can widen `connect-src` to the vault REST + live-query WS origins without touching the ceremony default. Pinned by `test/csp.test.ts` (the policy helper, the nonce threading, injection safety, and a render-scan of every ceremony page for the one thing a naive CSP breaks — an un-nonced inline `<script>`).
- **SPA CSP (P1.1.5, 0.0.8-rc.56)**: the SPA shell is a SEPARATE surface (Static-Assets-served, bypasses `htmlResponse`) with its own policy in `src/spa-csp.ts` — see the serving note above. Strict `script-src` (`'self'` + the derived inline-theme-script hash, no `unsafe-inline`) but a deliberately WIDE `connect-src 'self' https: wss:` (PW4 two-tier — the SPA MUST reach arbitrary user-named vault origins, D10) and wide passive `img-src`/`media-src` (remote markdown media + `blob:` attachments). The security value is the `script-src` lock + `object-src 'none'`/`base-uri 'self'`/`frame-ancestors 'none'`, not connect-src.

## Critical rule: shared core + shared wire contract, forked runtime

The engine is `@openparachute/core` (in parachute-vault) — never reimplement schema/query/MCP-tool semantics here; PR core changes upstream (they must keep the bun suite green). The WIRE contract (REST shapes, OAuth flows, MCP discovery, portable-md bytes) must match the bun vault byte-shaped — that's what keeps the Notes PWA, Claude connectors, and export-anytime working identically. The RUNTIME (router/DO/R2/D1) is cloud-specific by design. Cross-runtime drift is caught by the conformance suites — extend them with every endpoint you add.
